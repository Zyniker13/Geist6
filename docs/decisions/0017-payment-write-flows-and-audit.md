# 0017 — Payment write flows, audit log, and the three-gate write refusal

## Context

M4b adds the first writes: refunds on charges (full/partial + reason), captures
(charge and payment intent, full/partial + receipt email), payment-intent
confirm and cancel (+ reason), and canceling a pending refund. The product is
read-first: money-affecting actions must never run by accident, never run
twice, and never run while the user is only *looking* at the account.
Dashboard mode (M2) already refuses every non-GET at the client, but M2 knew
nothing about the account's dashboard lock after client creation, and nothing
in the app recorded what had been sent.

## Decision

Writes live behind **three independent gates**, each able to refuse on its own:

1. **UI gate** — `HomeView` builds a `PaymentsWriteService` only when
   `!account.dashboardLock`; detail views receive `writer: PaymentsWriteService?`
   and render their Actions menu only if it is non-nil. A locked account has
   no write UI at all.
2. **Service gate** — the service checks `client.mode == .dashboard` *or* a
   live `DashboardLockProvider` closure (reads the account's current lock from
   `AccountStore` through a weak `Sendable` box) before every write, and
   throws + records a refusal in the audit log if locked. This covers a lock
   flipped mid-session, after the writer was built.
3. **Client gate** — `StripeClient` refuses every non-GET in dashboard mode
   before anything reaches the network (M2, unchanged; the floor).

Every write call:

- carries an **idempotency key** generated by the service and stored in the
  audit entry before the request is sent, so a retry repeats exactly one
  request;
- is recorded in a **file-backed audit log** (`AuditEntry`: action, object,
  account, key, request ID, outcome, time) under Application Support — no API
  keys, no user data beyond Stripe object IDs;
- goes through a **sheet + confirmation dialog**: the sheet collects
  parameters (amount in cents, reason, receipt email), shows the parsed money
  amount inline, and the destructive dialog button performs the write;
  failures are shown inside the sheet so the user can retry, successes
  dismiss the sheet and surface a result alert.

Action menus are **status-gated**: refund appears only when the charge has
amount left to refund; capture only when something is capturable; confirm
only for `requires_confirmation`; cancel only for the interactive intent
statuses; cancel-refund only for `pending` refunds.

The write service is hand-written (not generated) because it composes
requests, idempotency, and audit; it uses the generated client's `perform`
and the generated param objects. The client's decoder became `public` so the
service can decode raw responses to capture the request ID.

## Consequences

- A dashboard-mode account cannot send a write through any path; proven by
  service-level tests (refusal + audit entry, mid-session lock) and a UI test
  asserting no Actions control exists.
- The audit log is append-only JSON lines; no UI for it yet (a future
  milestone can surface it).
- stripe-mock echoes fixtures for writes, so UI tests assert flow completion
  (dialog → action → success alert) while state transitions are covered by
  service-level fixture tests.
- Confirmation dialogs are the single write path; no swipe-action or
  context-menu writes.
