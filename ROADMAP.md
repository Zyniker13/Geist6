# Roadmap

Geist6 is a native iPad app for running one or more Stripe accounts: a fast, clear **dashboard** for anyone who needs to see what is happening, and a full **management interface** for anyone allowed to act. It connects straight to the Stripe API from the device, with no server of its own, and aims to cover every part of Stripe that a client app can reach through the API: payments, customers, billing, balances and payouts, Connect, disputes and fraud, reporting, tax, Terminal, Issuing, Treasury, Identity, and the rest.

This roadmap runs from an empty repository to version **v1.0.0**, ready for the App Store, in sixteen milestones (M0 to M15). Each milestone ends with a **Done when** line. A milestone is done only when that line is met and shown with real output from the same checks CI runs.

Priorities, in order, when they conflict: **safety of the user's money and keys, then correctness, then privacy, then clarity, then breadth of features.** A feature that can move money by accident, show a wrong figure, or leak a key is a regression, however useful it is.

## Before Building: Stripe Research and Plan Review (M0)

This roadmap was written from general knowledge of Stripe. Stripe changes often, so the first task is to check every claim here against Stripe's own current documentation and API definition, and to rebuild the feature list from them. No app code is written until M0 is done.

### M0.1 Gather the Sources

Fetch and keep local copies (outside the repository, or summarized in your own words inside it; never commit Stripe's text verbatim):

- Stripe's documentation index for tools: `https://docs.stripe.com/llms.txt`. Most documentation pages are also available as Markdown by adding `.md` to the page URL; use that form to read them.
- The API reference: `https://docs.stripe.com/api`, including the list of API versions and the changelog (`https://docs.stripe.com/changelog`), and the upgrade notes for the current version.
- Stripe's official OpenAPI definition, `https://github.com/stripe/openapi` (the `spec3.json` or `spec3.sdk.json` file for the current version, and the v2 definitions if present). This is the machine-readable source of truth for every resource, field, endpoint, enum, and expandable property.
- Stripe's official mock server, `stripe-mock` (`https://github.com/stripe/stripe-mock`), and the Stripe CLI, which are the test tools for M1.
- The pages on: API keys, restricted API keys and their permissions, key security and where keys may be stored, OAuth and Stripe Apps (including how a third-party app gets access to someone else's account, and whether that needs a server), Connect and the `Stripe-Account` header, sandboxes and test mode, API versioning and the `Stripe-Version` header, idempotency, pagination, the Search API and its availability, expanding responses, metadata, rate limits, errors, the Events API and how long events are kept, webhooks and event destinations, the v2 API (thin events, v2 accounts, and anything else under `/v2`), and Stripe's trademark and brand guidelines for third-party apps.

### M0.2 Write the Research Notes

In `docs/stripe/`, write in your own words:

1. **`api-inventory.md`**: every product area and every resource in the current OpenAPI definition, generated by a script (`Tools/inventory`) that reads the spec and lists each resource with its endpoints (list, retrieve, create, update, delete, search, and custom actions such as `capture`, `cancel`, `finalize`, `pay`, `void`, `close`), and which API version the inventory was built from. The script is committed and reruns in CI against the pinned spec, so the inventory can never drift from the spec silently.
2. **`coverage-matrix.md`**: one row per resource and action, with the milestone that covers it, the screen or flow it appears in, the tier of support (see [Tiers of Support](#tiers-of-support)), and the restricted-key permission it needs. Every resource in the inventory must have a row. A row may say "out of scope" only with a reason (for example, an endpoint that only makes sense on a server, or one Stripe marks as private preview).
3. **`access.md`**: every way the app could get access to an account, with what Stripe recommends for a client app with no server, what each way can and cannot do, how it is set up, and how it is revoked. At least: a restricted key the user creates; a secret key (allowed only with a warning; see [Keys and Safety](#keys-and-safety)); OAuth through Stripe Connect or a Stripe App, including whether the token exchange needs a server and what that would mean for this project; and Connect platform access to connected accounts. Record the decision as decision 0003.
4. **`permissions.md`**: the restricted-key permission for every resource and action (read, write, or none), and the two recommended permission sets: **Dashboard** (read-only on everything the app shows) and **Management** (read plus write on what the app can change). Note whether Stripe offers a link or template that pre-fills a restricted key's name and permissions, and if so, exactly how it works.
5. **`limits.md`**: rate limits (live and test), page sizes, the Search API's limits and freshness, how long the Events API keeps events, file upload sizes, and anything else that bounds what the app can show or how often it can refresh.
6. **`versioning.md`**: the API version the app pins, how Stripe-Version is sent, how the app handles fields and objects that are newer or older than the pinned version (accounts can be on different default versions), and the plan for upgrading the pinned version later.
7. **`brand.md`**: what the app may and may not call itself, and how it may refer to Stripe, per Stripe's guidelines.

## Fixed Choices

These are the starting choices. M0 may change one, but only with a decision record that explains why.

- **Platform:** a native iPad app in Swift 6 and SwiftUI, for the newest iPadOS that Xcode on the build machine supports and one version back (set in M1 and recorded). iPad is the only primary target. The app also runs on Apple silicon Macs as an iPad app; a native Mac or iPhone layout is [After v1.0.0](#after-v100).
- **A portable core.** Everything that is not user interface (the Stripe client, the generated models, pagination, search, caching, the permission map, metrics, formatting of money, and the account store's logic) lives in a Swift package that builds and tests with only the Swift toolchain, on macOS and on Linux, with `swift build` and `swift test`. Apple-only frameworks (Keychain, SwiftUI, Charts, App Intents, WidgetKit) stay in thin layers above it.
- **No server.** The app talks to `api.stripe.com` (and `files.stripe.com` and `connect.stripe.com` where needed) directly, with the user's own key. There is no project server, no proxy, and no relay. If M0 finds that a feature Stripe offers needs a server (for example, receiving webhooks, or an OAuth token exchange that needs a client secret), that feature is out of scope for v1.0.0 and listed in [After v1.0.0](#after-v100) with the reason.
- **No tracking.** No analytics, advertising, crash-reporting, or third-party SDKs that send data anywhere. The only network peer is Stripe. The target App Store privacy label is "Data Not Collected."
- **Generated from Stripe's definition.** The API models and endpoint descriptions are generated from Stripe's official OpenAPI definition, pinned to one version in the repository, by a generator in this repository. Hand-written code is for the client, the UI, and the logic; never hand-write a model the generator can produce.
- **License:** all rights reserved (see `LICENSE`): the repository is public for reference only. Never add an open-source license or a contributing guide. Dependencies must use permissive licenses (MIT, BSD, Apache-2.0, or similar), each listed in `THIRD_PARTY.md`; nothing under copyleft terms.
- **Versioning:** `vA.B.C`, where A is a major release or rewrite, B a feature release, and C a fix or small change. Tags are `vA.B.C`. Each finished milestone from M3 on may be tagged `v0.B.0`; launch is `v1.0.0`.
- **Name:** "Geist6" is a working name. M0 records a short list of candidate product names that follow Stripe's brand guidelines (decision 0006); choosing the final name is a maintainer item, needed by M15.

## Tiers of Support

"Full support" means every resource Stripe exposes reaches the user somehow. Not every resource needs a hand-built screen, so each row in the coverage matrix has one of three tiers:

| Tier | What the user gets | Used for |
| --- | --- | --- |
| **1: Crafted** | Hand-built screens and flows designed for that job: lists with the right columns and filters, a detail view that reads like a story, the common actions one tap away, and charts where they help | The everyday work: payments, refunds, disputes, customers, subscriptions, invoices, products and prices, balances, payouts, Connect accounts, and the home dashboard |
| **2: Structured** | A generic but readable list, detail, and edit view generated from the resource's definition: labelled fields, money and dates formatted, related objects linked, enums as pickers, and every documented action as a button with the right confirmation | Everything else with a stable API: Terminal, Issuing, Treasury, Tax, Identity, Climate, Financial Connections, Entitlements, Forwarding, reporting, files, webhook endpoint management, and so on |
| **3: Explorer** | The API Explorer ([M10](#m10-api-explorer-and-full-coverage)): any endpoint, with parameters filled from a form built from the spec, the raw response, and copy-as-curl, gated by mode and permissions | Endpoints too new, rare, or unusual for tier 2, and power users |

The coverage matrix may move a resource up a tier at any time. It may only move one down with a decision record.

### Package Layout

| Target | Purpose |
| --- | --- |
| `StripeSpec` | The pinned OpenAPI definition (as a resource), its loader, and the inventory used by the coverage checks |

| `Tools/inventory` | Builds `docs/stripe/api-inventory.md` from the spec and checks the coverage matrix |
| `App` (Xcode project, via XcodeGen) | The SwiftUI iPad app, Keychain storage, widgets, App Intents, and system integration |

### Data and Caching

- The app is a view onto Stripe. Stripe is the source of truth; the app never shows a cached figure as current without saying when it was fetched.
- A local cache (SQLite through a well-known, maintained library, chosen in decision 0005) holds recent objects per account and mode, so the app opens instantly and works read-only offline, clearly marked as offline. The cache holds no keys and can be cleared at any time without losing anything.
- Aggregates on the dashboard (volume, net, refunds, disputes, new customers, MRR, churn, and so on) are computed from the data Stripe returns, with the method written down in `docs/metrics.md` and tested against hand-checked fixtures. Where Stripe provides a figure directly (balances, report runs), use Stripe's figure.
- Activity and notifications come from the Events API, polled while the app is open and in background refresh, because a client app cannot receive webhooks. The app says plainly that background alerts can be late.

### Keys and Safety

- **Keys live only in the Keychain**, per account and mode, never in files, logs, the cache, screenshots, crash output, or the clipboard after setup. The Keychain item is device-only by default; syncing keys through iCloud Keychain is a per-account opt-in with a clear explanation.
- **Restricted keys first.** Setup recommends a restricted key with the Dashboard or Management permission set from `docs/stripe/permissions.md`. A secret key (`sk_`) is accepted only after a clear warning and is always shown with a badge. A publishable key (`pk_`) is rejected with an explanation.
- **Two modes per account.** *Dashboard* mode never sends a write request, enforced in `StripeClient` (not only in the UI), and tested. *Management* mode allows writes the key permits. The user can lock any account to Dashboard mode even if its key allows more.
- **The permission map.** On setup and on a schedule, the app learns what the key may do (from Stripe where it says so, and otherwise by cheap read-only probes such as `limit=1` list calls), and hides or disables what the key cannot do, with a message that says which permission to add. It never probes with a write.
- **Every write is deliberate.** Every request that changes anything carries an idempotency key where Stripe accepts one: all `/v1` POST requests, and `/v2` POST and DELETE requests (Stripe documents idempotency keys as effective on those verbs only; `/v1` DELETE is idempotent by definition). Money-moving or irreversible actions (refunds, payouts, transfers, cancellations, voids, closing a dispute, deleting) need a confirmation that restates the amount, currency, account, and mode, and optionally Face ID or the passcode. Live mode is always visibly marked. Every write is recorded in a local audit log (what, when, which account, the request ID) that the user can view and export.
- **Test data first.** Every write flow is built and tested against `stripe-mock` and, where the maintainer provides one, a Stripe sandbox, before it is enabled for live mode.

### Setup: the Shortest Path

The goal is that a new user goes from opening the app to seeing their dashboard in under two minutes, without reading documentation.

1. Choose **Dashboard** or **Management**, with one sentence each on what it means.
2. The app shows the exact permissions to grant and, if Stripe supports a pre-filled restricted-key link (M0, `permissions.md`), opens it; otherwise it opens the API keys page and lists the boxes to tick.
3. Paste the key, or scan it as a QR code shown on another device. The app checks the key's prefix and mode, calls `GET /v1/account`, shows the account's name and country, and shows what the key can and cannot do.
4. Optionally add the matching test-mode or sandbox key, name the account, pick a colour, and set Dashboard lock or Face ID for writes.

Adding a second account is the same flow from the account switcher. If M0 finds a shorter path that Stripe supports with no server (for example, an OAuth flow that works entirely on the device), use it and record why.

## Milestones

Each milestone builds on the ones before it. Feature milestones (M4 to M11) each cover their rows of the coverage matrix: tier-1 screens are built as described; tier-2 rows get the generated views from M10 early, as soon as M10's descriptor layer exists.

### M1: Foundation

- Repository layout above; `Package.swift`; XcodeGen `project.yml`; SwiftLint and swift-format configs; `scripts/check.sh` that runs everything CI runs; CI on GitHub Actions (Linux job for the package; macOS job for the app, using the newest Xcode the hosted image has, with actions pinned to full commit SHAs and read-only permissions). Never pin a Swift version or a `setup-swift` action against the image's SDK.
- `stripe-gen`: generates models for the pinned spec version, with lossless decoding, polymorphic types, expandable fields (`ID or object`), and nullable versus missing fields kept distinct. CI regenerates and fails on any diff.
- `StripeClient` with everything listed in the package layout, against `stripe-mock` in tests (both CI jobs run `stripe-mock`).
- Decisions 0001 to 0006 confirmed or revised from M0.

**Done when:** `scripts/check.sh` passes locally and in CI; the generator produces compiling models for every object in the pinned spec; the client's contract tests list, retrieve, create, update, delete, search, paginate (forward and back), expand, upload a file, and handle every documented error type against `stripe-mock`; and a Dashboard-mode client is proven by a test to refuse every non-GET request.

### M2: Accounts, Keys, and Setup

- The account store (Keychain), the setup flow above, test and live keys per account, sandboxes, account colours and names, Dashboard lock, Face ID for writes, key rotation and removal, and the permission map.
- Connect platforms: list connected accounts and act on one through `Stripe-Account`, with the connected account clearly shown.
- A first runnable app: account switcher, the account's details, and an empty home screen.

**Done when:** UI tests add, rename, lock, and remove two accounts against `stripe-mock`; unit tests show keys never reach the cache, logs, or exports; the permission map hides and explains a feature the key cannot use; and setup from launch to the account screen takes at most five taps after pasting a key (recorded UI-test step count).

### M3: App Shell and Home Dashboard

- Sidebar navigation, a global search (Stripe's Search API where available, list filters otherwise, and IDs pasted directly), a universal "open by ID" for any Stripe object ID, pull to refresh, and offline marking.
- Home: balances by currency, today and period volume, net, refunds, disputes, successful and failed payments, new customers, upcoming payouts, and recent activity from the Events API; period and currency pickers; Swift Charts.
- iPad essentials from the start: split view, multiple windows (one account per window), keyboard shortcuts, pointer support, and Dynamic Type.

**Done when:** the home figures match hand-checked fixtures for at least three currencies including a zero-decimal one; search finds objects by ID, email, and amount against `stripe-mock`; and UI tests open two windows on two different accounts.

### M4: Payments

PaymentIntents, Charges, payment methods and their types, Refunds (full, partial, and with reason), Checkout Sessions, Payment Links, SetupIntents, captures and cancellations, the payment timeline (from the PaymentIntent, its charges, refunds, disputes, and balance transactions), receipts (decision 0021: surfaced through the charge's receipt fields and hosted receipt link — Stripe's OpenAPI definition models no standalone Receipt resource), filters by status, amount, date, customer, and method, plus the tier-2 rows that ride along with payments: Mandates, Confirmation Tokens, and the PaymentIntent amount-details line items (decision 0022: built early in M4 as compact structured views — mandate detail linked from the SetupIntent detail, confirmation tokens and mandates through open-by-ID and search, line items as a section on the PaymentIntent detail).

**Done when:** every payments row in the coverage matrix is built at its tier; refund and capture flows pass UI tests against `stripe-mock` with confirmation and idempotency checked; and no write control appears in Dashboard mode (UI test).

### M5: Customers

Customers, their payment methods, balance and cash balance, tax IDs, addresses, invoices, subscriptions, payments, and events in one view; create, edit, and delete; customer search; and the customer portal link where Stripe supports creating one.

**Done when:** every customers row in the matrix is built at its tier, with UI tests for create, edit, and delete against `stripe-mock`.

### M6: Billing

Products, Prices, Subscriptions (create, update with proration preview, pause, resume, cancel now or at period end), Subscription Schedules, Invoices (draft, edit lines, finalize, send, pay, void, mark uncollectible), Invoice line items and invoice rendering, Credit Notes, Coupons, Promotion Codes, Quotes, Billing Meters and meter events (usage), the Customer Portal configuration, Tax Rates, test clocks (test mode only), and billing metrics (MRR, ARR, churn, trial conversion), computed as `docs/metrics.md` says.

**Done when:** every billing row in the matrix is built at its tier; subscription and invoice lifecycle UI tests pass against `stripe-mock`; and the billing metrics match hand-checked fixtures.

### M7: Balances, Payouts, and Reporting

Balance and balance transactions with fees, Payouts (list, detail with the transactions in each payout, create, and cancel where allowed), Transfers and reversals, Top-ups, report types and report runs (run, wait, and download), and CSV export of any list.

**Done when:** every row is built at its tier; a payout's transactions reconcile to the payout amount in a fixture test; and report runs download and open in the Files app (UI test).

### M8: Connect

Connected accounts (list, detail, capabilities, requirements, and verification status), account links and login links for Express accounts, transfers and application fees and their refunds, payouts on connected accounts, the v2 accounts API (GA for Connect platforms and in preview otherwise: the app covers its rows at tier 2 when a platform key uses it), connected-account persons, external accounts, and account sessions.

**Done when:** every Connect row is built at its tier; a platform test shows every screen working on a connected account through `Stripe-Account`; and the active connected account is always visible (UI test).

### M9: Disputes and Fraud

Disputes with deadlines, evidence editing (text and file uploads), submission, and acceptance; early fraud warnings; Radar reviews (approve and refund), value lists and items, and the risk details on each payment.

**Done when:** every row is built at its tier; dispute evidence upload and submission pass UI tests against `stripe-mock`; and dispute deadlines appear on the home screen and in a widget.

### M10: API Explorer and Full Coverage

- The tier-2 engine: list, detail, edit, and action views generated from the spec's descriptors, with formatting for money, dates, enums, expandable objects, metadata, and nested objects.
- The tier-3 API Explorer: every endpoint in the spec, a form for its parameters, the raw response, copy-as-curl with the key redacted, and history; Dashboard mode limits it to GET.
- Bring every remaining matrix row to its tier: Terminal (readers, locations, configurations), Issuing (cardholders, cards, authorizations with approve and decline, transactions, disputes), Treasury (financial accounts, flows), Tax (settings, registrations, calculations, transactions), Identity (verification sessions and reports), Climate, Financial Connections, Entitlements, Forwarding, Files and file links, webhook endpoint management, Apple Pay domains, shipping rates, and anything else in the inventory.

**Done when:** `Tools/inventory` reports that every in-scope resource and action in the pinned spec is reachable in the app at its tier or higher (a CI check, not a manual count), and the explorer passes contract tests for every endpoint that `stripe-mock` serves (all of `/v1`) against `stripe-mock`, with `/v2` endpoints covered by recorded response fixtures written by hand with obviously fake values, because `stripe-mock` implements only the `/v1` namespace.

### M11: Events, Alerts, and System Integration

The activity feed from the Events API with filters; alert rules (for example, a new dispute, a failed payout, a payment over an amount) checked in background refresh; local notifications; widgets (balance, today's volume, disputes due); App Intents and Shortcuts (read-only intents by default; write intents require Management mode and confirmation); Spotlight for recent objects; and share links that open the right object in Stripe's own Dashboard.

**Done when:** alert rules fire in a test with a recorded events fixture; widgets and intents pass their tests; and no intent can write in Dashboard mode (test).

### M12: iPad Experience

Stage Manager and external displays, drag and drop (objects as IDs or CSV), context menus everywhere, a complete keyboard-shortcut set with the discoverability overlay, Apple Pencil-friendly controls where they help, and state restoration per window.

**Done when:** the UI tests and a recorded manual pass in `TESTING.md` cover every item.

### M13: Security, Privacy, and Accessibility

- A security review against `docs/security.md` (threat model: a lost device, a shared iPad, a malicious file or QR code, a leaked screenshot, a compromised clipboard, and a key with more permissions than it needs); the privacy manifest; App Transport Security with no exceptions; a privacy screen in the app switcher; and auto-lock after inactivity.
- Accessibility: VoiceOver labels for every figure and chart, Dynamic Type to the largest sizes, sufficient contrast, Reduce Motion, and the automated accessibility audits in UI tests.
- Localization-ready strings, with English complete; money, dates, and numbers formatted for the user's locale.

**Done when:** every item in `docs/security.md` is checked and recorded, the accessibility audits pass on every screen, and a full UI-test run passes at the largest Dynamic Type size.

### M14: Performance and Reliability

Budgets: cold start to a cached home screen under one second on the base iPad simulator; any list scrolls at 120 fps on ProMotion simulators; rate limits never cause a user-visible failure (backoff and queueing, tested with `stripe-mock` errors); and memory stays bounded with 100,000 cached objects. Long-run soak tests for background refresh.

**Done when:** the budgets are met and recorded in `TESTING.md` with the device, date, and build.

### M15: Release Preparation

App Store metadata drafts, screenshots generated by UI tests, the privacy label, the age rating questionnaire, a support page and privacy policy drafts (for the maintainer to publish), the final name and brand check against Stripe's guidelines, TestFlight and submission (maintainer items), and a release checklist.

**Done when:** everything the build agent can prepare is in `docs/release/`, every remaining maintainer item is filed, and `v1.0.0` is tagged once the maintainer confirms submission.
